# Intake-package email failure surfacing and telehealth room hardening (v2)

This pass re-reviews the branch after commit 8ecd18b. The Cognito `RESEND` wrapper is gone and replaced by a single mapping for `UnsupportedUserStateException` to a 409 with Forgot-password guidance, so the misleading relabel and the status flattening from v1 no longer exist. Recording discard now keys off a flag set at the moment consent is withdrawn, with pure helpers in `lib/ehr/recording-discard.ts` and behavior tests. The create-path concern is closed: the only `POST` create caller (`full-production-interface.tsx:997`) sends `sendInvitation: false`, so no invite email is attempted there. What remains is one data-handling gap in the discard logic and some cleanup.

Watch for: (1) discard is only armed on the data-message and consent-effect paths; when the provider's poll sees `next.recording` flip off because the client withdrew, the recording is stopped but uploaded (likely). (2) `joinErrorRef` stays set after an unexpected stop, so later room-state notices are suppressed until the next join (possible, carried from v1).

**Verdict**: NEEDS_CHANGES

## High-level view

The Cognito fix is now minimal and correct in scope: one error type, one actionable message, everything else flows through the existing handling. The email gating chain is unchanged from v1.

The discard design improved: the decision is captured when consent is withdrawn rather than read at stop time, which removes the parent-prop timing risk. It is incomplete, because only two of the three withdrawal signals arm the flag, so a provider can still upload audio after the client withdrew consent.

## Discard flag coverage across withdrawal signals

The flag is set in three places: the `rlth-consent` data-message handler, the provider effect when `recordingConsent` goes false, and the poll's `clientWithdrew` branch. The third is dead: `clientWithdrew` requires `!provider`, and `shouldDiscardRecording` returns false for non-providers, so it neither discards nor matters. Meanwhile the poll's other trigger, `!next.recording`, is the path a provider would hit if the server records the client's withdrawal, and it stops the recorder with the flag unset. The data message and the poll are redundant signals for the same event, but only one is wired to discard. Because the consequence is uploading audio the client withdrew consent for, this is the blocking item.

```
client withdraws
  ├─ data message 'withdrawn'  -> flag armed -> discard
  └─ poll: next.recording=false -> stopRecording() only -> upload
```

## Cognito resend mapping

Mapping `UnsupportedUserState` to a 409 keeps the original status semantics, and the message directs staff to the right workaround. Other failures keep their prior handling. The check precedes the "already exists" branch, which is harmless.

## Closed from v1

Create-path email status: only one create call site exists and it opts out of invitations, so surfacing `inviteEmailStatus` there is unnecessary. Consent timing: resolved by the flag design, apart from the gap above. Both new test files now execute real helper code for the decision logic.
