# Intake-package email failure surfacing and telehealth room hardening

The branch makes "Send Intake Package" report SES failures instead of marking the invitation Sent. The resend response now carries `emailDelivered`, a new helper maps `inviteEmailStatus` to staff-readable text, and the UI marks the invitation Failed with a red message when the email did not go out. In `native-telehealth-room.tsx`, an unexpected Chime stop keeps its reason on screen and locks the status poll, stale poll responses can no longer tear down a fresh join, and recordings stopped after provider consent is withdrawn are discarded rather than uploaded. Nothing existing was removed or moved. The diff is additive, apart from one rewritten failure string and a rewrapped Cognito call.

Watch for: (1) the new catch around Cognito `RESEND` relabels every failure, including throttling, outages and permission errors, as "already has a portal account that cannot be re-invited", and echoes the raw Cognito detail to the browser (confirmed). (2) The new-patient creation path still returns `inviteEmailStatus` that no UI code reads, so SES failure is surfaced only on resend (likely). (3) The consent-discard guard reads parent props at `onstop` time and could drop a legitimate recording if the parent clears consent when the call ends (possible).

**Verdict**: NEEDS_CHANGES

## High-level view

The email fix is a thin, consistent chain: the server derives a boolean from the existing status string, and the UI gates the "Sent" state on it. The helper treats anything other than an explicit "sent" as undelivered, so a missing or unknown status fails closed. The one structural risk is the new error wrapping around the Cognito resend call, which hides the real cause of non-"user exists" failures behind a single misleading message.

The telehealth changes are small, local and match existing patterns (`joinErrorRef`, `requestedAt` comparisons, latest-value refs). Intentional leave still goes through `disconnectLocal`, which clears `session.current` before Chime stops, so the new `audioVideoDidStop` path only runs for unexpected stops. The consent-withdrawal discard is the one behavior that can lose data, and it depends on prop timing that the tests only check as source text.

## Cognito resend error wrapper

The resend branch now catches any failure from the Cognito call and throws a fixed message saying the patient "already has a portal account that cannot be re-invited automatically", followed by the underlying message. That copy is accurate for the case the author had in mind (a user in CONFIRMED state, where RESEND is rejected). The catch is unconditional, though. A throttle, a missing IAM permission, a bad region or a network error all show the same "cannot be re-invited" text, which sends staff to the Forgot-password workaround when the real fix is infrastructure. The status logic is also lopsided. A caught `ApiError` with a 4xx keeps its status, while any other error, including an upstream 5xx, becomes 502. `cognitoAdmin` throws `ApiError(500, …)` when the region is missing, and that case is also flattened to 502. The raw detail is returned to the browser, which may include Cognito internals. Narrow the wrapper to the specific Cognito error types.

## Email delivery gating in the resend flow

`emailDelivered: inviteEmailStatus === "sent"` is added next to the existing `inviteEmailStatus`, so existing consumers are unaffected. In the UI, `resendPatientInvitation` marks the profile Failed, shows the message and returns `false` before reaching the Sent update. The caller at the saved-patient card only sets `invitationSent` on `true`, so the button label stays correct. The helper's `not-configured` text says the server has no AWS credentials, which matches `ses-send.ts` (returns `not-configured` only when no access key resolves).

The asymmetry is the create path. `POST` for a new client sets `inviteEmailStatus` from `sendPatientInviteEmail` and returns it. A grep of `app/ehr` shows `describeInviteEmailStatus` is used only in the resend handler. If staff create a patient and the email fails, the UI behavior is unchanged from before.

## Telehealth: unexpected stop, stale poll, consent discard

`audioVideoDidStop` now receives the Chime status code, builds a reason, sets `joinErrorRef` so the poll does not overwrite it, and shows the text in both the notice and the camera notice. The `session.current !== meeting` guard still protects the user-initiated paths. `joinedAt` is compared with the poll's `requestedAt` on the same client clock, so skew is not an issue. Because `joinErrorRef` is only cleared on the next join start or on `audioVideoDidStart`, room-state notices stay frozen after a drop.

The discard path in `capture.onstop` depends on refs updated during render, and the existing effect at the top of the file calls `stopRecording()` when `recordingConsent` becomes false. In that sequence the ref is current by the time `onstop` fires. When the stop comes from leaving or ending the call, the ref values depend on whether the parent clears `sessionForm` first. This was not traced into the parent. The only caller that passes these props (`full-production-interface.tsx:3866`) provides all three, so the ref defaults of `false` do not discard by accident. The `upload` change to read `onRecordingReadyRef` is a safe fix for stale closures.

## Test coverage

Both new test files use `fs.readFileSync` plus regexes against component source, and the status-mapping test is the only one that runs real code. Not tested: the actual poll-versus-join ordering, discard-on-withdrawal behavior, the 502/4xx mapping in the clients route, and the create-path email status. `tsc` and `next build` were not run (offline sandbox). Reading the types, `sessionStatus?.statusCode?.()` fits `MeetingSessionStatus.statusCode()`, and `result?.emailDelivered` is fine because `productionApi` results are untyped in this file. I found no TypeScript error by reading, but that is not a substitute for a build.
