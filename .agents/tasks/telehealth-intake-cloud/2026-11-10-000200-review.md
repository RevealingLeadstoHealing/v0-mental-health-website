# Intake-package email failure surfacing and telehealth room hardening (v3)

This pass re-reviews the branch after commit e170a49. The dead `recordingConsentRef` and `providerConsentRef` are gone (grep confirms no remaining references in source or tests). The v2 blocker, poll-driven discard, is resolved by documentation: the report now explains why the poll path is not armed. Checking the server confirms the reasoning. `clientRecordingConsent` is also `false` for a client who never consented in a provider-run session, so a provider's poll cannot tell "withdrew" from "never consented" and arming discard there would drop legitimate recordings. Withdrawal is instead signalled by the `rlth-consent` data message, which the client sends before the `consent` API call, so it reaches the provider ahead of any poll that could observe the server change.

Watch for: (1) if the `rlth-consent` data message is lost, a provider's recorder stops via the poll and the audio is uploaded despite withdrawal (possible, narrow, accepted trade-off). (2) Most telehealth tests are source-text regexes (confirmed).

## High-level view

Recording discard depends on a client-to-provider data message as the single withdrawal signal. That is the only channel carrying the distinction the server state cannot express, so the design is sound, with a residual loss window if the message does not arrive.

## Single-channel withdrawal signal for discard

The server clears `recording` both when a provider stops and when a client withdraws, and it leaves `clientRecordingConsent` false for clients who never opted in. The poll therefore cannot infer withdrawal, which is why `discardOnStop` is armed only from the data message and the provider's own consent toggle. The client sends the data message before awaiting the `consent` call, so the ordering favors the discard path. The residual risk is a dropped message with no fallback, as noted in the issue list.
